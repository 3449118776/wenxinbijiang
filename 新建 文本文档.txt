# 文心笔匠前端核心模块审计报告

## 一、严重 Bug

### 【严重 Bug 1】cloud-sync.js:171-180 — 本地编辑后永远无法同步到云端（版本号比较逻辑根本性错误）

这是三个文件中最严重的缺陷。`smartSync` 中版本比较逻辑如下：

```
var localVersion = lw._version || 0;
var cloudVersion = cloudMap[lw.id] ? (cloudMap[lw.id].version || 0) : 0;
if (cloudVersion === 0 || localVersion > cloudVersion) → push
else if (cloudVersion > localVersion) → pull
else → unchanged
```

作品的 `_version` 字段**仅在云端同步成功后由服务端返回值赋值**（cloud-sync.js:239、250、274、281），在本地任何编辑路径（`saveWork`、`save`、`saveImmediate`、章节内容修改）中**从不递增**。

同步时序推演：
1. 新建作品，`_version` 为 undefined → 0，云端无 → push，服务端返回 version=1，本地 `_version=1`
2. 用户编辑章节内容，`_version` 仍为 1
3. 下次 `smartSync`：localVersion=1，cloudVersion=1 → 走 `else` 分支 → `unchanged` → **不推送**
4. 此后所有本地编辑都不会被推送，除非云端版本因其他设备推送而升高

`db.js:957-964` 中 `saveImmediate` 会触发 `_cloud.smartSync()`，因此每次保存后的自动同步都命中"unchanged"分支。**云端同步对编辑场景完全失效，只有首次创建能同步。**

### 【严重 Bug 2】db.js:1301-1308 + 1327/1334/1485/1491 — `flush()` 不落盘导致删除/恢复操作可能丢失

`flush()` 实现：
```
flush() {
  if (this._saveTimer) { clearTimeout(this._saveTimer); this._saveTimer = null; }
  if (this._savePending) {
    this._savePending = false;
    return this.saveImmediate(false);
  }
  return true;  // ← 没有待保存时直接返回 true，不写盘
}
```

而 `deleteWork`(1485)、`hardDeleteWork`(1491)、`restoreFromTrash`(1327)、`emptyTrash`(1334) 都仅调用 `this.flush()`。这些方法只修改了内存中的 `this.works` / `this._trash`，若此时 `_savePending` 为 false（即 800ms 内没有其他 `save()` 调用），`flush()` 直接返回 true 而**不调用 `saveImmediate()`**，内存修改未写入 localStorage。用户若此时关闭页面，删除/恢复操作丢失，下次打开数据恢复原状。这些方法应调用 `saveImmediate()` 或 `save()` 而非 `flush()`。

### 【严重 Bug 3】db.js:1049-1071 — 存储拆分时子字段写入失败导致旧数据被删除（数据丢失）

`_autoSplitWorks` 中，先收集所有 `wxbj_w_*` 旧 key 到 `keysToClean`，写入成功后才从 `keysToClean` 移除。但写入与移除的顺序为：

```
try {
  ...
  localStorage.setItem(subKeyName, jsonStr);   // 1049 行，可能抛 QuotaExceededError
  var cleanIdx2 = keysToClean.indexOf(subKeyName);  // 1050 行
  if (cleanIdx2 >= 0) keysToClean.splice(cleanIdx2, 1);  // 1051 行
} catch(subErr) { ... }
```

`cleanIdx2` 的移除在 `setItem` **之后**。若 `setItem` 因配额超限抛异常，该 subKeyName 仍留在 `keysToClean` 中，随后在 1069-1071 行被 `localStorage.removeItem(oldKey)` 删除。结果：**新数据写不进去，旧数据反而被清掉**，该字段（如 `longMemory`、`world`、`outline`）彻底丢失，`_stitchHeavyWork` 读回时为 undefined。

### 【严重 Bug 4】api.js:4-6 — `file://` 协议下 API_BASE 完全失效

```
const API_BASE = (location.hostname === 'localhost' || location.hostname === '127.0.0.1')
  ? 'http://localhost:8787/api'
  : location.origin + '/api';
```

`file://` 协议下 `location.hostname` 为空字符串，既非 localhost 也非 127.0.0.1，走 else 分支。此时 `location.origin` 在多数浏览器中为字符串 `"null"`，因此 `API_BASE = "null/api"`。所有经代理的调用（`testApiKey`、`_callOnce` 的 `/ai/chat`）fetch 到 `"null/api/ai/chat"` 必然失败。免费模式（api.js:566 直接 fetch 外部 URL）不受影响，但所有需要后端代理的 AI 调用和密钥测试在本地双击打开 HTML 时全部不可用。cloud-sync.js:487-490 的自动初始化有同样问题。

### 【严重 Bug 5】cloud-sync.js:188-209 — 硬删除的作品会从云端"复活"

`smartSync` 遍历云端作品时，若本地不存在且不在 `_trash` 中，则执行 `toPull.push(cw.workId)`（206 行）拉取到本地。但 `hardDeleteWork`（db.js:1489-1492）物理删除作品时**不入回收站**，因此下次同步时该作品既不在本地也不在 trash → 被判定为"云端有本地无" → 重新拉回本地。用户硬删除的作品会不断从云端复活，无法真正删除。只有 `deleteWork`（软删除入 trash）才会触发云端删除（203-204 行）。

## 二、数据丢失风险

### 【数据丢失风险 1】cloud-sync.js:470-481 — `_mergeWork` 全字段覆盖，本地独有数据被冲掉

`_mergeWork` 用 `Object.keys(cloudPayload)` 遍历云端字段直接赋值给本地作品（除 `_version`、`_writing`）。这是破坏性覆盖：
- 本地的 `_fingerprint`、`_slimMeta`、`_shardId`、`_slim` 等运行时字段若云端 payload 中有对应键（即使值为空），会被覆盖
- **章节内容风险最大**：若本地章节已从 IndexedDB 分片加载了完整 content，而云端 payload 中的 chapters 是瘦身过的（content 为空或仅元数据），`_mergeWork` 会用云端的空 chapters 覆盖本地完整 chapters，导致章节正文丢失

### 【数据丢失风险 2】cloud-sync.js:306-320 — `quickSync` 无版本比较直接推送

`quickSync` 直接 `pushWork(_packWork(w))`，不比较本地与云端版本号。若本地版本落后于云端（其他设备已推送更新），`quickSync` 仍会用旧数据覆盖云端新数据。虽然代码中未见 `quickSync` 被自动调用，但作为公开 API 一旦被调用即有覆盖风险。

### 【数据丢失风险 3】cloud-sync.js:426-444 — `pushKeysAndSettings` 整体覆盖云端，多设备设置互踩

`pushKeysAndSettings` 用 PUT 整体覆盖云端 keys 和 settings。两台设备各自有不同设置时，后推送的设备覆盖先推送的设备。`syncKeysAndSettings`(370-423) 的拉取合并只补充 `undefined`/`''` 字段，不更新已有字段、不处理删除。组合效果：设备 A 改了 `theme=dark`，设备 B 改了 `fontSize=18`，A 推送后云端 `theme=dark,fontSize=15`，B 推送后云端 `theme=blue,fontSize=18`，A 的 theme 丢失。

### 【数据丢失风险 4】db.js:1476-1483 — 大于 2MB 的作品删除后不可恢复

`deleteWork` 仅在 `JSON.stringify(target).length < 2*1024*1024` 时才入回收站。超过 2MB 的作品被直接从 `this.works` 移除且不进 trash，用户无法恢复，也没有任何提示。对于长篇小说（几十万字很常见），单部作品超 2MB 是正常的。

### 【数据丢失风险 5】db.js:1152-1155 — 拆分存储后章节正文不参与 stitch，依赖 IndexedDB 分片

`_stitchHeavyWork` 注释说明 chapters 是轻量化的，正文需从 IndexedDB 懒加载。但 `_makeLightWorks`(1074-1109) 生成的轻量 chapters 只保留 title/_slim/_shardId/wordCount/confirmed，content 被丢弃。若 IndexedDB 中的 `wxbj_app_memory_v1` 数据库被清除（浏览器清理、隐私模式、跨域隔离失效），章节正文将永久丢失，因为 localStorage 中只存了轻量索引。localStorage 拆分 key（`wxbj_w_*`）也不含 chapters content。

### 【数据丢失风险 6】cloud-sync.js:211-227 — 回收站中的作品触发云端永久删除

`smartSync` 检测到本地作品在 trash 中时，执行 `deleteWork` 删除云端作品（214 行）。这意味着：设备 A 软删除作品（进 trash）→ 同步 → 云端删除。设备 B 从未拉到该作品。此后只有 A 的本地 trash 保留该作品 30 天。若 A 期间清空回收站或 30 天过期，作品彻底消失，无法跨设备恢复。

## 三、性能问题

### 【性能问题 1】db.js:953-954 — 每次 saveImmediate 都全量写所有章节分片

`saveImmediate` 中：
```
try { this.saveAppMemoryMirror(json); } catch(mirrorErr) {}
try { this.saveAllChapterShards(); } catch(shardErr) {}
```
`saveAllChapterShards`(399-407) 遍历**所有作品的所有章节**，每章开一个 IndexedDB 事务（`saveChapterShard` 内 `openAppMemoryDB` + transaction）。对于多作品/多章节用户，每次 800ms 防抖保存触发 O(作品数 × 章节数) 次 IndexedDB 写操作。而 `markWorkShardsDirty` + `flushDirtyChapterShards` 已实现增量脏页刷新机制，`saveAllChapterShards` 在此属于冗余全量写。同时 `startAutoMaintenance`(304-309) 每 60 秒也调用一次 `saveAllChapterShards`，进一步叠加写入压力。

### 【性能问题 2】api.js:203 — `API_MAX_KEY_RETRY = 999` 导致极端情况下超长重试

`callRealAPI` 中 `baseTotal = Math.min(keys.length, 999)`，`total = baseTotal + 2`。若用户导入大量密钥（如 999 个），单服务商最坏情况 1001 次尝试，每次超时 90 秒，理论最坏耗时约 25 小时。虽然 `API_MAX_TOTAL_TRY = 40` 限制跨服务商尝试，但该限制在 `callRealAPIWithFallback` 中只对**服务商数**计数（855 行 `totalTry++` 每个服务商只加 1），不限制单服务商内的 key 尝试次数。

### 【性能问题 3】db.js:1289-1298 — `save()` 防抖返回 true 但无法感知实际写入结果

`save()` 立即返回 true，实际写入在 800ms 后异步执行。调用方无法得知 `saveImmediate` 是否成功。对于需要确认落盘的场景（如导出前、页面关闭前），需显式调用 `flush()`，但 `flush()` 又有 Bug 2 中描述的问题。

### 【性能问题 4】cloud-sync.js:324-330 — 自动同步无并发保护，可能重叠执行

`startAutoSync` 用 `setInterval` 每 5 分钟调用 `smartSync()`，不检查上一次同步是否仍在进行。若网络慢导致一次同步超过 5 分钟，多个 `smartSync` 会并发执行，争抢 `_version` 写入和 `DB.works` 修改，产生竞态。`db.js:957-964` 中 `saveImmediate` 触发的 3 秒防抖 `smartSync` 与定时器同步也可能重叠。

### 【性能问题 5】api.js:691 — `opts.signal` 事件监听器泄漏

```
if (opts.signal) { try { opts.signal.addEventListener('abort', function(){ ac.abort(); }); } catch(e){} }
```
每次 `_callOnce` 尝试都给 `opts.signal` 添加一个 `abort` 监听器，但从不移除。在 `callMultiAI`(967-976) 中 `sharedSignal` 被传给所有并行 `callRealAPI`，每个又会给 `opts.signal` 添加多个监听器（每个 key 尝试一个）。请求完成后监听器仍挂在 signal 上，造成内存泄漏。

## 四、健壮性问题

### 【健壮性问题 1】api.js:714-721 — 429 同 key 重试仅在非静默模式下生效

429 重试逻辑位于 `else if (!opts.silent && e && e.kind === 'rate')` 分支内。当 `opts.silent === true` 时（`callRealAPIWithFallback` 中非首选服务商 859 行 `silent: oi !== 0`；`callMultiAI` 中所有服务商 971 行 `silent: true`），整个 rate 分支被跳过，429 错误直接走到 727 行 rotate 逻辑，**立即切换下一个 key，不等待 3 秒、不重试同一个 key**。这与注释"429 频率限制：等待 3 秒后重试同一个 key（最多重试 2 次）"矛盾。实际效果：跨服务商回退和多 AI 并行模式下，429 不会重试同 key。

### 【健壮性问题 2】api.js:308 + 929-996 — `currentKeyIndex` 全局共享，并发调用互相干扰

`currentKeyIndex` 是模块级全局对象（308 行），`getAiKey`/`rotateApiKey` 读写它。`callMultiAI`(965-976) 并行调用多个 `callRealAPI`，每个内部又可能 `rotateApiKey`，并发修改同一个 `currentKeyIndex[provider]`，导致 key 选择不可预测（可能重复选同一个 key、跳过某些 key）。JavaScript 单线程下不会数据竞争，但逻辑上 rotate 的时序会让 key 轮询行为不符合预期。

### 【健壮性问题 3】api.js:700 — `onProgress` 回调名为流式进度但实际无流式处理

## 五、其他建议

### 【其他建议 1】api.js:265-275 — 免费端点硬编码 `sk-free`/`sk-or-v1-anonymous` 占位 key

`FREE_ENDPOINTS` 中的 key 值如 `'sk-free'`、`'sk-or-v1-anonymous'` 是占位符，实际多数服务商不接受此类 key。免费模式大概率全部 401 失败，最终返回 `generateLocal` 占位文本。建议明确标注免费模式可用性不可保证，或移除已失效的端点。

### 【其他建议 2】api.js:907 + 911-915 — 全部失败后静默返回占位文本

`callRealAPIWithFallback` 在所有服务商失败后返回 `generateLocal(prompt)` 的硬编码占位字符串（"【AI 暂不可用】..."）。该字符串会被当作正常 AI 输出返回给上层，上层若未检测该前缀（`callMultiAI` 972 行有检测 `indexOf('AI 暂不可用')`），可能将占位文本写入作品正文。建议返回 `null` 并由上层统一处理。

### 【其他建议 3】db.js:78 + 93 — `APP_DATA_VERSION` 与迁移逻辑脱节

`window.APP_DATA_VERSION = 44` 定义后，`init()` 迁移用硬编码 12，`saveImmediate` 用硬编码 44，`buildSnapshot`/`buildBackupPayload` 也用硬编码 44。建议统一引用 `APP_DATA_VERSION` 常量，避免版本号散落多处难以维护。

### 【其他建议 4】cloud-sync.js:448-468 — `_packWork` 将整个 work 作为 payload 上传

`payload: w` 包含完整 work 对象（含 `_fingerprint`、`_slimMeta`、`_writing` 等运行时字段）。批量推送时 `pushBatch` 将多个完整 work 打包成一个请求体，大作品 + 多作品易超出服务端请求体大小限制。建议上传前剥离运行时字段，并对批量大小做分片。

### 【其他建议 5】db.js:80-84 + cloud-sync.js — `_version` 字段命名冲突

DB 根数据对象的 `_version`（数据文件版本，当前 44）与 work 对象的 `_version`（云端同步版本号）同名但语义完全不同。`_packWork`(cloud-sync.js:464) `version: w._version || 0` 读取的是 work 的同步版本，而 `saveImmediate`(db.js:920) `_version: 44` 是数据文件版本。两者无冲突但极易混淆，建议 work 同步版本改名为 `_syncVersion`。

### 【其他建议 6】api.js:685-686 — `total = baseTotal + 2` 的 +2 余量在非 429 场景产生冗余重试

非 429 错误（如全部 key 都 invalid）时，`+2` 额外尝试会因 `getAiKey` 的模运算重复尝试已失败的 key。虽然 727 行 `if (keys.length > 1 && attempt < total - 1)` 在 `attempt` 达到 `total-1` 时会 break，但中间仍有多余的 key 重复尝试。建议 429 重试使用独立计数器而非混入 `total`。

### 【其他建议 7】db.js:999-1072 — `_autoSplitWorks` 无原子性保证

拆分写入多个 localStorage key 的过程非原子。若中途页面关闭（如 `visibilitychange` 触发 flush 时正在拆分），部分子字段已写、部分未写，`_stitchHeavyWork` 读回的数据不完整。建议先写完整快照到临时 key，再原子替换，或写入后校验完整性。

### 【其他建议 8】cloud-sync.js:256-289 — 拉取并发限制为 3 但无总超时

`toPull` 分批并发 3 个 `getWork`，但无整体超时。若云端响应慢，`smartSync` 可能长时间阻塞，配合【性能问题 4】的并发同步会导致多个 smartSync 堆积。

## 【严重 Bug】

### B1. 环境变量 `WXBJ_SECRET` 实际不生效，JWT 永远使用硬编码密钥（致命）
- `_shared.js:4` —— `export const JWT_SECRET = globalThis.__JWT_SECRET || 'wxbj_cloud_secret_2026_v2';`
- `_middleware.js:24-26` —— 在请求时才 `globalThis.__JWT_SECRET = context.env.WXBJ_SECRET`
- `[[route]].js:50` —— `await jwt_verify(token)`（不传 secret）
- `[[route]].js:90,109,153` —— `jwt_sign({...}, null, 30*24*3600)`

`_shared.js` 的 `JWT_SECRET` 是模块顶层 `const`，在模块首次 import 时求值（此时 isolate 刚加载，`globalThis.__JWT_SECRET` 尚未被任何 middleware 设置），因此被永久固定为硬编码字符串 `'wxbj_cloud_secret_2026_v2'`。`jwt_sign/jwt_verify` 内部用 `secret || JWT_SECRET`，调用方传 `null/undefined`，所以始终走 `JWT_SECRET` 常量。**middleware 后续写入 `globalThis.__JWT_SECRET` 完全无效**。配合 B2，任何人都能伪造任意用户 token。

### B2. JWT 密钥硬编码且前后端不一致
- `_shared.js:4` 默认值 `'wxbj_cloud_secret_2026_v2'`
- `backend/auth.js:5` 默认值 `'wxbj_cloud_secret_2026'`（无 `_v2`）

两套后端默认密钥不同，若都未配置环境变量则 token 互不通用；且该默认值存在于源码仓库中，公网可查，等于无密钥。

### B3. `handle_forgot` 把重置验证码直接返回客户端（账户接管）
- `[[route]].js:132` —— `return json_response({ ok: true, code: code, token: code });`

任何人用任意邮箱调用 `/auth/forgot-password` 即可拿到该邮箱的重置码，再调 `/auth/reset-password` 重置密码。注释自称"演示模式"，但这是完整的未授权账户接管链路。`[[route]].js:122-125` 的"不区分是否存在"防枚举逻辑也因此被废掉——对已存在用户直接返回 code。

### B4. `verify_password` 的 bcrypt 兼容分支直接 `return false`，旧用户全部被锁死
- `_shared.js:123-126` —— 注释称"降级支持 bcrypt"，实际 `return false`

若 KV 中存在任何 bcrypt 哈希（`$2a$`/`$2` 开头）的用户，这些用户永远无法登录。与 `backend/auth.js` 用 `bcryptjs` 的实现不兼容，迁移用户会全员失效。

### B5. `db_create_user` 用户 ID 自增 + 非原子操作，并发注册产生重复 ID / 数据覆盖
- `_shared.js:175-185` —— 读 `user:nextId` → +1 → 写回，三步非原子
- KV 最终一致性下，两个并发注册可能读到相同 nextId，导致 `user:id:<n>` 互相覆盖、`user:nextId` 回退。
- 同邮箱并发注册也存在 TOCTOU：`_shared.js:173` 检查 existing 与 `183` 写入之间无锁，两个相同邮箱可同时创建。

### B6. `db_upsert_work` 版本号逻辑导致无版本号时永远无法更新
- `_shared.js:255-258` —— `clientVersion = parseInt(body.version) || 0`；`if (clientVersion <= rec.version && rec.version > 0) return unchanged`

客户端若未传 `version`（或传 0），`clientVersion=0`，对已存在作品（version≥1）恒为 `unchanged`，更新被静默丢弃。这是版本冲突设计的副作用陷阱，前端一旦漏传 version 即"同步失效但无报错"。

### B7. `random_code` 用 `Math.random()` 生成验证码
- `_shared.js:280-282` —— `String(Math.floor(100000 + Math.random() * 900000))`

`Math.random()` 非密码学安全。应使用 `crypto.getRandomValues`（项目里 `random_hex` 已正确用了，验证码却没有）。

### B8. `_middleware.js` 未用 try-catch 包裹 `context.next()`
- `_middleware.js:29` —— `const response = await context.next();`

下游 `onRequest` 抛出未捕获异常时（例如 `setKVStore` 或 `jwt_verify` 内部异常逃逸），异常直接传播，CORS 响应头不会被追加，浏览器端跨域请求会拿到不可读的错误响应，且前端无法获得结构化错误。

### B9. `handle_ai_test` 超时定时器在 `continue` 路径的清理依赖 catch 块
- `[[route]].js:316-406` —— 每个模型迭代创建 `ac`/`tid`，正常成功路径在 `352` 行 `clearTimeout`，但若 `resp.text()`（`354`）抛异常进入 `399` catch，`clearTimeout` 在 `400` 执行后 `continue`。逻辑可工作，但 `for...of` 中跨迭代的定时器管理脆弱，且最坏 3 个模型 × 25s = 75s 墙钟时间，极易超出 Pages Functions 时长限制被强杀，客户端收到 524 而非自定义错误。

### B10. `handle_work_delete` 未校验作品是否存在即返回成功
- `[[route]].js:232-245` —— 直接 `store.delete(key)` 后返回 `{ok:true}`，对不存在的 workId 也返回成功；且 `list.filter` 后 `store.put` 与并发 upsert 存在竞态（删作品时另一请求在改 works 列表，可能把已删除的 workId 重新加回）。

## 【性能问题】

### P1. `db_list_works` 典型 N+1 KV 读取
- `_shared.js:197-220` —— `works:<userId>` 存的是 workId 数组，再逐个 `store.get(key_work(...))` 取元数据。N 个作品 = 1 + N 次 KV 读取。KV 单次读取延迟较高，作品多时列表接口会非常慢且昂贵。应将作品元数据冗余进列表值，或用 KV 列表 + 缓存。

### P2. `handle_batch` 串行处理，无并发
- `[[route]].js:217-225` —— `for (const it of items) await db_upsert_work(...)`，每个 item 内部又是多次 KV 读写（`_shared.js:236,248,251,268`），串行叠加。批量同步 50 个作品可能触发平台超时。可用 `Promise.all` 并发（注意 KV 并发写入限制）。

### P3. `db_upsert_work` / `db_update_user` 双写冗余
- `_shared.js:248-251,268`（works 列表 + work 记录，创建时 4 次 KV 操作）
- `_shared.js:193-194`（`user:email:` + `user:id:` 双写）
- 数据为查询便利做了双写冗余，但无事务保证，部分失败会导致两份数据不一致（如 `user:id:` 更新成功而 `user:email:` 失败）。

### P4. 无任何缓存层
- 用户信息、作品列表、设置每次请求都直读 KV，未使用 Cache API 或边缘缓存。`/user/profile`、`/works` 这类高频接口尤其受益于短 TTL 缓存。

### P5. 大 payload 反复序列化
- 作品 payload（整本书内容）在 `db_upsert_work`（`_shared.js:238`）`JSON.stringify`，在 `db_list_works`（`_shared.js:208`）又对每个作品 `JSON.stringify`，`handle_work_get`（`[[route]].js:186`）又 `JSON.parse`。大对象反复序列化消耗 CPU（Pages Functions CPU 时间有限）。

### P6. `handle_ai_test` 串行尝试多模型
- `[[route]].js:315-407` —— 最多 3 个模型串行，最坏 75s。可改为并发竞速（`Promise.any`）取第一个成功结果。

## 【其他建议】

### O1. 与 `backend/` 大量代码重复，应统一
- `[[route]].js` 的 `handle_register/login/forgot/reset/profile/works_list/work_get/work_upsert/batch/delete` 与 `backend/routes.js` 几乎逐行对应；`_shared.js` 的 JWT/密码哈希与 `backend/auth.js` 重复。

### O2. `AI_PROVIDERS` / `AI_TEST_MODELS` 硬编码于路由文件
- `[[route]].js:250-299` —— 22 个服务商配置写死在路由代码中，且前端 `assets/js/api.js` 也有类似服务商清单，三处重复维护。应抽到独立配置文件或 `_shared.js`，前后端共享。

### O3. 死代码 / 未使用导入
- `[[route]].js:6` 导入 `random_hex` 但路由内未使用
- `_shared.js:150` `key_snap` 定义但从未调用（见 R3）
- 建议清理或补全快照功能

### O4. 每次请求重复 `setKVStore`
- `[[route]].js:16-18` 每次请求都 `setKVStore(context.env.WXBJ_DATA)`；而 `_middleware.js:20-22` 已把 env 挂到 `globalThis`，`KV()`（`_shared.js:135-143`）会兜底从 globalThis 读取。两套机制并存冗余，且 `_kvStore` 模块级变量跨请求驻留（同 isolate 内），逻辑不清晰。建议统一为单一来源。

### O5. 路由匹配方式脆弱且重复
- `[[route]].js:61,65,69,74` 多处用 `apiPath.match(/^\/works\/[^\/]+$/)` + `apiPath.split('/')[2]` 提取参数，正则与 split 混用，易出错。`[[route]].js:69-72`（DELETE）与 `74-77`（POST `/delete`）两个入口指向同一 handler，重复。建议引入轻量路由表（method + 路径模式 → handler）统一分发。

### O6. `KV()` 兜底全局扫描过于宽泛
- `_shared.js:135-143` 依次尝试 `WXBJ_DATA / WXBJ_USERS / KV / DB / DATA / STORE` 全局变量，可能误绑定到无关全局（尤其叠加 S5 的 env→global 暴露后）。应显式指定唯一 binding。

### O7. `handle_ai_chat` 未校验 `messages` 结构
- `[[route]].js:419,435` —— `messages` 直接透传上游，未校验是否为数组、元素是否含 `role/content`。非法结构会导致上游 400，错误经 S7 回显。Claude 分支（`[[route]].js:431-444`）把 system 消息分离后 `filteredMsgs` 可能含空 content，上游可能拒绝。

### O8. `handle_batch` 无 items 数量上限
- `[[route]].js:215` —— `const items = body.items || []` 无长度限制，恶意客户端可传超大数组导致长时间运行 + KV 写入风暴，叠加 P2 串行更易触发超时。建议加硬上限（如 100）。

### O9. OPTIONS 处理重复
- `[[route]].js:24-34` 与 `_middleware.js:7-17` 都处理 OPTIONS 并设 CORS 头；`json_response`（`_shared.js:284-294`）也带 CORS 头。三处重复，维护时易遗漏其中一处。

## 三、cloud-sync.js 实际同步的字段

### 3.1 `smartSync()`（L147-301）—— 仅同步 works，不同步其它

逐行分析后确认 `smartSync` 同步的内容：
- **同步 works**：通过 `getWorks()` → `getWork()` 拉取，通过 `pushBatch()` / `pushWork()` 推送。`_packWork()`（L448-468）打包的字段为：`workId, title, category, synopsis, payload(=整个 work 对象), version, chapterCount, totalWords`。
- **读取 `_trash`**（L184）：仅用作"判断云端作品是否应删除"的信号——若云端作品在本地 `_trash` 中，则调用 `deleteWork()` 删除云端。**`_trash` 数组本身不上传到云端**。
- **不同步**：`apiKeys`、`apiConfig`、`settings`、`custom_templates`、`predict_platform`、IndexedDB 任何 store。

### 3.2 `syncKeysAndSettings()`（L370-423）—— 拉取密钥与设置

- `GET /user/keys` → 合并 `apiKeys`（云端有但本地没有的补充进来）+ 合并 `apiConfig`（仅本地为空时填充）
- `GET /user/settings` → 合并 `settings`（仅本地 `undefined` 的 key 填充）
- 合并策略为"只补不覆盖"，不会用云端覆盖本地已有值。

### 3.3 `pushKeysAndSettings()`（L426-444）—— 推送密钥与设置

- `PUT /user/keys`，body=`{apiKeys, apiConfig}`（整体覆盖云端）
- `PUT /user/settings`，body=`{settings}`（整体覆盖云端）

### 3.4 触发时机（Grep 确认）

| 函数 | 触发位置 | 时机 |
|---|---|---|
| `syncKeysAndSettings` | index.html L345 | **仅登录成功后**调用一次 |
| `pushKeysAndSettings` | settings.html L465, L585 | **仅设置页保存**时调用 |
| `smartSync` | index.html L347（登录后）、db.js L962（本地保存后防抖 3s）、startAutoSync 定时器（5min） | 自动 + 登录 |

**关键缺口**：`startAutoSync`（L324-330）的定时器**只调用 `smartSync`，不调用 keys/settings 同步**。即用户在非设置页修改 apiKeys/apiConfig/settings 后，若不主动进设置页保存，不会自动推送到云端。

## 八、需要补充云端同步的数据清单（按重要性排序）

### P0 — 严重（存在数据丢失风险）

1. **已瘦身章节的正文内容（IndexedDB `chapters` 分片）**
   - 问题：`safeSlimCurrentWork()`（db.js L639-666）将旧章节 `content` 置空并标记 `_slim=true`，正文仅存于 IndexedDB 分片。但 `_packWork()`（cloud-sync.js L448-468）直接序列化 `w`，瘦身章节上传到云端的 payload 中 `content=''`。smartSync 拉取后 `_mergeWork` 用云端空 content 覆盖本地，导致**瘦身章节正文在多设备间永久丢失**。
   - 建议：推送前对瘦身作品执行"缝合"（从 IndexedDB 分片还原 content），或在云端为章节分片建立独立同步通道。

### P1 — 高（跨设备体验严重缺失）

2. **`_trash` 回收站数据**
   - 问题：回收站仅本地，不跨设备。设备 A 删除作品后云端被删，设备 B 既无作品也无回收站记录，无法恢复。
   - 建议：新增 `/user/trash` GET/PUT 端点，将 `_trash` 数组纳入云端同步；或在云端删除时改为"软删除"标记而非物理删除。

3. **`custom_templates` 自定义模板**
   - 问题：用户精心制作的自定义模板仅存 localStorage，换设备/清缓存即丢失。
   - 建议：新增 `/user/templates` GET/PUT 端点，纳入 `syncKeysAndSettings`/`pushKeysAndSettings` 流程。

### P2 — 中（功能完整性受损）

4. **Pages Functions 缺失云端快照端点**
   - 问题：cloud-sync.js 的 `getSnapshots()`/`restoreSnapshot()` 调用 `/works/:workId/snapshots` 与 `/restore`，但 `[[route]].js` 未实现，Pages 部署下返回 404，云端版本回滚功能不可用。
   - 建议：在 `[[route]].js` 与 `_shared.js` 中补齐快照列表/恢复端点（参考 backend/routes.js L244-288）。

5. **`chapter_history` 章节历史版本**
   - 问题：章节编辑历史仅存 IndexedDB，换设备丢失所有历史版本，无法跨设备回溯。
   - 建议：按需同步（可仅同步最近 N 条），新增 `/works/:workId/chapters/:idx/history` 端点。

6. **IndexedDB `backups` 自动备份**
   - 问题：本地自动备份不跨设备，设备损坏则备份全失。
   - 建议：可将最近一次内部备份镜像到云端（如复用 `/user/settings` 模式新增 `/user/backup`）。

7. **apiKeys/apiConfig/settings 自动同步缺口**
   - 问题：`startAutoSync` 定时器（cloud-sync.js L324-330）只调 `smartSync`，不调 `pushKeysAndSettings`。用户在写作页等非设置页修改密钥/配置后，需等到下次登录或手动进设置页保存才同步。
   - 建议：在 `smartSync` 末尾追加 `pushKeysAndSettings` 调用，或独立设置定时器。

8. **backend/routes.js 缺失 `/user/keys` 与 `/user/settings`**
   - 问题：若部署 Node 后端，密钥与设置同步会全部 404。
   - 建议：将 Pages Functions 的 `handle_keys_*`/`handle_settings_*` 逻辑移植到 backend/routes.js。

### P3 — 低（体验优化）

9. **`predict_platform` 预测平台偏好**
   - 问题：仅本地，换设备需重选。可纳入 settings 一并同步。

10. **UI 状态（`last_edit_work`/`last_edit_chapter`/`wxbj_last_page`）**
    - 问题：不跨设备恢复上次编辑位置。属体验优化，非数据安全。

### 3. `autoSync: true` 配置完全无效（cloud-sync.js:22-26, 324-330, 490）

第一个 script 块（第 130-132 行）正确处理 localhost：

但第二个 IIFE 内（第 138 行）重新定义为：

## 【安全问题】

### 1. Token 存储在 localStorage，易受 XSS 攻击（index.html:141-148, cloud-sync.js:39-47）

`wxbj_cloud_token` 和 `wxbj_cloud_user` 存于 localStorage。任何 XSS 漏洞均可直接读取并外传 token。更安全的方案是 HttpOnly + Secure + SameSite cookie。结合下方多处 XSS 风险，此问题被放大。

### 2. 找回密码流程直接在前端展示验证码（index.html:252-266）

`showResetPanel` 将服务端返回的 `data.code` 直接渲染到页面（第 256 行）：
```js
(code ? '<p ...><b>验证码：' + code + '</b><br>...' : '')
```
注释说明"本版本为单机使用，直接展示验证码"。这意味着任何人只需调用 `/auth/forgot-password` 即可获取任意邮箱的重置验证码，进而重置任意账号密码。这是**可被任意账号接管**的严重漏洞。

### 3. 找回密码/重置密码页面存在 XSS（index.html:256, 265, 302）

- 第 256 行：`'邮箱：' + email` 直接拼入 innerHTML，`email` 来自用户输入（第 234 行 `forgot-email`）。
- 第 265 行：`onclick="submitResetPassword(\'' + email + '\')"` 将 email 注入 onclick 属性，若 email 含单引号可逃逸。
- 第 302 行：`'已登录账号：' + email`，email 来自 `getUser().email`，若注册时 email 含 HTML 字符则可触发。

### 4. 更新检测弹窗存在 XSS（index.html:420-427）

`showUpdateDialog` 用 `insertAdjacentHTML` 注入 `data.version`、`data.releaseNotes`（第 422-423 行），这些值来自远程 `version.json`。若该 JSON 被篡改或 CDN 被劫持，可注入任意 HTML/JS。`releaseNotes` 用 `white-space:pre-wrap` 渲染，未做任何转义。

### 5. architecture.html 人物关系图存在 XSS（architecture.html:833）

`showRelationGraph` 用正则从 `work.chars` 提取名字后直接拼入 HTML：
```js
html += '<div ...>' + names[i] + '</div>';
```
未调用 `he()` 转义。若人设内容含 `<img onerror=...>` 等标签，会被执行。

### 6. "清除所有数据"未清理云端凭据（settings.html:825-834）

`clearAllData` 仅删除 `wxbj_data_v4`，**不清除** `wxbj_cloud_token`、`wxbj_cloud_user`、`wxbj_last_update_check`、`last_edit_work`、`last_edit_chapter`。用户以为"清除所有数据"后登出，实则云端 token 仍在，且 `window.cloud` 内存中的 token 也未清。

### 7. settings.html 密钥列表虽掩码但通过 DOM 可见（settings.html:418-422）

`renderKeyList` 对密钥做了 `key.substring(0,6)+'****'+key.substring(key.length-4)` 掩码，但完整密钥仍存在于 `DB.apiKeys`（内存）和 localStorage（`wxbj_data_v4`）。任何同源脚本可读取。掩码仅防肩窥，不防 XSS。这一点本身是本地存储密钥的固有局限，但应在文档中明确告知用户。

### 8. settings.html 批量导入密钥无长度/格式硬校验（settings.html:492-587）

`addNewKeys` 通过 `_parseKeyLine` 解析，`_looksLikeKey`（第 590-598 行）仅要求 `length >= 8` 且不含中文。任意 8 字符以上的英文字符串都会被当作密钥测试，可能向服务商发送大量无效请求（虽每个都经 `testApiKey`，但无频率限制）。

### 1. 全局变量污染严重

- `work-list.html` 和 `architecture.html` 都在全局作用域定义 `_currentLevel`、`_selectedWorkId`、`selectedModule`、`MODULE_INFO`、`he()`、`getWorkById()`、`goToLevel()`、`handleGlobalBack()`、`updateBreadcrumb()`、`selectWork()`、`selectModule()`、`renderLevel1~4()`、`getCurrentWork()` 等同名函数。虽分属不同页面无冲突，但大量重复代码，建议抽取公共模块。

### 2. architecture.html 对 `switchArchModule` 和 `generateArchModule` 做了 monkey-patch（第 759-779, 2388-2400）

```js
var _origSwitchArchModule = window.switchArchModule;
window.switchArchModule = function(mod){ ... };
```
这种模式在脚本只执行一次时安全，但若未来引入热重载或重复加载，会形成调用链导致栈溢出。建议改为直接定义或用事件驱动。

### 3. write.html 无内联脚本，全部依赖外部 JS

`write.html` 的所有逻辑在 `write-editor.js`（约 5000+ 行）等外部文件中。本次审计重点检查了自动保存（第 261-274 行）、章节切换（第 437-455 行）、`visibilitychange`/`beforeunload` 落盘（第 4938-4973 行）。落盘逻辑较完善，但 `_flushEditorToWork`（第 4939-4951 行）的 `catch(e){}` 静默吞错，用户不会知道保存失败。

### 4. 离线编辑冲突处理缺失

`write-editor.js` 的 `saveChapter`（第 457-474 行）和 `_flushEditorToWork`（第 4939-4951 行）仅写本地 DB，无版本号比对。`smartSync`（cloud-sync.js:147-300）用 `_version` 字段比对，但本地保存时不递增 `_version`，只有 `pushWork` 成功后才更新（第 239、250 行）。若用户离线编辑后另一设备也编辑了同一章节，两端 `_version` 相同，`smartSync` 会判定为 `unchanged`（第 178-180 行），**静默丢失一端修改**。建议本地保存时递增 `_version` 或引入 `updatedAt` 时间戳。

### 5. settings.html `setActiveKey` 直接操作 `DB.flush()`（settings.html:741-753）

```js
const selected=keys.splice(index,1)[0];
keys.unshift(selected);
DB.flush();
```
直接修改 `DB.getApiKeys()` 返回的数组引用并 `flush`，依赖 `getApiKeys` 返回的是内部数组的引用而非副本。若 DB 实现改为返回副本，此函数将失效。应通过显式 API（如 `DB.setApiKeys`）操作。

### 6. work-list.html `confirmDelete` 云端删除失败时静默继续（work-list.html:1064-1076）


云端删除失败仅 `console.warn`，本地照常删除。结果：本地已删但云端仍存，下次 `smartSync` 时云端该作品会被当作"本地不存在"拉回（cloud-sync.js:205-207），导致已删作品复活。应删除失败时提示用户并中止，或记录待删队列。

### 7. index.html `showToast` 与 work-list.html `showToast` 签名不一致

`index.html`（第 366-375 行）接受 `(msg, opts)`，支持 `opts.duration`、`opts.error`。`work-list.html`（第 1122-1127 行）仅接受 `(msg)`，固定 2 秒。`settings.html` 调用 `showToast(msg, {type:'success', duration:5000})` 但其 `showToast` 来自 `ui.js`（未审计）。三套实现易混淆。

### 8. architecture.html `formatReaderContent` 的 `escapeHtml` 不转义单引号（architecture.html:997-1003）

## 总结

最关键的问题集中在**登录/同步链路**：`index.html` 的登录/登出函数与 `window.cloud` 实例状态完全脱节（只操作 localStorage，不更新内存），导致登录后同步不触发、登出后同步仍用旧 token。这是整个云端同步功能的致命缺陷，建议优先修复 `setToken`/`clearToken` 使其同步调用 `window.cloud._saveToken()` / `_clearToken()`，或直接改用 `window.cloud.login()` / `logout()` 方法。

其次是**找回密码验证码前端展示**的安全漏洞，可导致任意账号被接管，应立即移除该展示逻辑或限制为开发环境。

XSS 风险点较多（index.html 的 email 拼接、更新弹窗的 releaseNotes、architecture.html 的人物关系图），建议统一使用已有的 `he()` 函数转义所有用户/远程内容后再插入 DOM。

## 🔴 P0 致命问题（必须立即修复）

### 1. 登录后云端同步链路完全失效
**位置**：[index.html:339-359](file:///workspace/index.html#L339-L359)、[cloud-sync.js:32-34](file:///workspace/assets/js/cloud-sync.js#L32-L34)

`submitCloudLogin` 调用页面内的 `setToken()`（只写 localStorage），**从不调用 `window.cloud._saveToken()`**。而 `window.cloud` 实例的 `this.token` 仅在构造时读取一次 localStorage。登录后 `isLoggedIn()` 仍返回 false，`syncKeysAndSettings → smartSync` 链路**永远不执行**。用户看到"登录成功，正在同步"toast，实际无任何同步发生。登出同理（`clearToken` 不清 cloud 实例内存）。

`JWT_SECRET` 是模块顶层 `const`，在模块首次 import 时求值（此时 `globalThis.__JWT_SECRET` 尚未被 middleware 设置），被永久固定为硬编码 `'wxbj_cloud_secret_2026_v2'`。middleware 后续写入完全无效。**任何人都能伪造任意用户 token**。且该默认值在源码仓库中公网可查。

### 3. 找回密码验证码直接返回客户端（账户接管）

`handle_forgot` 把重置验证码直接返回客户端，前端还把它渲染到页面。**任何人用任意邮箱调用 `/auth/forgot-password` 即可拿到重置码，重置任意账号密码**。

### 4. 本地编辑后 `_version` 不递增，同步对编辑场景完全失效
**位置**：[cloud-sync.js:171-180](file:///workspace/assets/js/cloud-sync.js#L171-L180)、[db.js](file:///workspace/assets/js/db.js)

作品的 `_version` **仅在云端同步成功后由服务端返回值赋值**，本地任何编辑路径（`saveWork`、`save`、章节修改）从不递增。同步时序：新建→push→version=1→编辑→version 仍=1→smartSync 判定 unchanged→**不推送**。此后所有本地编辑都不会被推送。整个云端同步对编辑场景形同虚设。

## 🟠 P1 严重问题（数据丢失/功能失效）

### 6. `flush()` 不落盘导致删除/恢复操作丢失
**位置**：[db.js:1301-1308](file:///workspace/assets/js/db.js#L1301-L1308)、1485/1491/1327/1334

`deleteWork`/`hardDeleteWork`/`restoreFromTrash`/`emptyTrash` 仅调用 `flush()`，而 `flush()` 在无待保存时直接返回 true 不写盘。若 800ms 内无其他 `save()`，内存修改未写入 localStorage，用户关闭页面后删除/恢复操作丢失。

### 7. 存储拆分配额失败时旧数据被删除（数据丢失）
**位置**：[db.js:1049-1071](file:///workspace/assets/js/db.js#L1049-L1071)

`_autoSplitWorks` 中 `setItem` 抛 QuotaExceededError 时，该 subKeyName 仍留在 `keysToClean`，随后旧 key 被 `removeItem`。**新数据写不进，旧数据反而被清掉**，字段（longMemory/world/outline）彻底丢失。

### 8. 瘦身章节正文不同步（多设备丢失正文）
**位置**：[db.js:639-666](file:///workspace/assets/js/db.js#L639-L666)、[cloud-sync.js:448-468](file:///workspace/assets/js/cloud-sync.js#L448-L468)

`safeSlimCurrentWork` 将章节 content 置空标记 `_slim=true`，正文仅存 IndexedDB 分片。但 `_packWork` 直接序列化 work，瘦身章节上传到云端的 payload 中 `content=''`。smartSync 拉取后 `_mergeWork` 用云端空 content 覆盖本地，**瘦身章节正文在多设备间永久丢失**。

### 9. 快照路由与快照保存逻辑缺失
**位置**：[[route]].js](file:///workspace/functions/api/[[route]].js) 缺失、[_shared.js:150](file:///workspace/functions/api/_shared.js#L150) `key_snap` 死代码

前端 `cloud-sync.js:131-138` 调用 `/works/:workId/snapshots` 和 `/restore`，但 Pages Functions 未实现，返回 404。更严重的是 `db_upsert_work` 完全没有快照写入逻辑，`key_snap()` 定义后从未被调用。**云端版本快照功能在 Pages 部署下完全不可用**。

### 10. 硬删除作品从云端"复活"
**位置**：[cloud-sync.js:188-209](file:///workspace/assets/js/cloud-sync.js#L188-L209)、[db.js:1489-1492](file:///workspace/assets/js/db.js#L1489-L1492)

`hardDeleteWork` 物理删除不入回收站。下次同步时该作品既不在本地也不在 trash → 被判定"云端有本地无" → 重新拉回。**硬删除的作品会不断从云端复活**。

### 11. 旧 bcrypt 用户全部被锁死
**位置**：[_shared.js:123-126](file:///workspace/functions/api/_shared.js#L123-L126)

`verify_password` 的 bcrypt 兼容分支注释称"降级支持"，实际 `return false`。KV 中任何 bcrypt 哈希用户永远无法登录。

### 12. `startAutoSync` 从未被调用，5 分钟自动同步不存在
**位置**：[cloud-sync.js:324-330](file:///workspace/assets/js/cloud-sync.js#L324-L330)

构造函数仅保存 `this.autoSync` 标志，但从不调用 `startAutoSync()`。`autoSync: true` 是死配置。
